# Building the Android apps

Both apps build **from their own source folder**. There is one master copy of
each app and one command to build it.

```
node tools/build-apk.js driver
node tools/build-apk.js client
```

The signed APK lands in `SMI-APKs/`.

---

## The two folders

| | Path | What it is |
|---|---|---|
| **Source (master)** | `apps/driver-app`, `apps/client-app` | The code. This is the only copy you edit. |
| **Output** | `SMI-APKs/` | The signed APKs the build produces. |

`apps/<app>/android/` is generated by the build and is gitignored. It is safe to
delete; the next build recreates it.

---

## What the command does

1. **Generates the native project** if `apps/<app>/android/` is missing
   (`expo prebuild --platform android --no-install`). The version comes from
   `app.json`, so the native project can never disagree with it.
2. **Applies the release signing config.** `expo prebuild` always emits a project
   that signs its release build with the *debug* key. The script corrects that,
   reading the keystore path from `android/gradle.properties`.
3. **Builds** with `gradlew assembleRelease --no-daemon`.
4. **Verifies** the built APK with `aapt`, comparing `versionCode`/`versionName`
   against `app.json`. It fails rather than shipping a mislabelled build.
5. **Copies** the APK to `SMI-APKs/<app>-v<version>.apk`.

Useful flags:

```
node tools/build-apk.js driver --clean      # regenerate android/ from scratch
node tools/build-apk.js driver --prebuild   # force a fresh prebuild
```

A clean build takes roughly 9 minutes. A rebuild with `android/` already in place
is faster, since Gradle reuses what has not changed.

## Why it used to be different

The apps were previously copied into `C:\Users\Chait\eas-builds\smi-{driver,client}`
and built there. Two things caused that:

- **Metro mistook the repository root for the project root.** With no
  `metro.config.js`, Metro walks up the directory tree, finds `apps/package.json`
  and the repository's own `node_modules`, and resolves modules from the wrong
  place. Each app now has a `metro.config.js` pinning the root to its own folder,
  which removes the problem.
- **The release signing config was not reproducible.** It had been hand-edited
  into the generated `build.gradle` in the build tree, so a fresh prebuild lost
  it. `tools/build-apk.js` now applies it every time.

Both are fixed, so the copies are unnecessary. Editing `apps/driver-app/App.js`
and running the build is all there is to it.

## Prerequisites

Already installed on this machine:

- **JDK 17** — `C:\Program Files\Microsoft\jdk-17.0.20.101-hotspot`
- **Android SDK** — `C:\Android\Sdk` (platform android-36, build-tools 36.0.0)
- **Keystore** — `C:\Users\Chait\.smi-keys\selectmobility-release.keystore`

Dependencies are installed per app. If `node_modules` is missing:

```
cd apps/driver-app
npm install --legacy-peer-deps --no-audit --no-fund --ignore-scripts
```

`--ignore-scripts` is not optional on this machine: Windows Defender interferes
with npm's package extraction and a plain `npm install` fails with a wall of
`TAR_ENTRY_ERROR EPERM`.

Override the build defaults with `JAVA_HOME`, `ANDROID_HOME`, `SMI_KEYSTORE`,
`SMI_KEYSTORE_PASSWORD` or `SMI_KEY_ALIAS` if any of them move.

## Changing the version

Edit `app.json` — **one file**:

```json
{
  "expo": {
    "version": "1.2.0",
    "android": { "versionCode": 4 }
  }
}
```

The next build picks both up, because the native project is regenerated from
`app.json` and the script checks the result. `versionCode` must increase for
Android to accept an update over an existing install.

## The keystore

`C:\Users\Chait\.smi-keys\selectmobility-release.keystore` is the apps' identity.
It is deliberately **outside the repository** — it is not source code and should
not travel with it.

**Back it up.** If it is lost, no future build can update an already-installed
app: Android only accepts an update signed with the same key, so every user would
have to uninstall and reinstall.

Check a built APK is signed with it:

```
C:\Android\Sdk\build-tools\36.0.0\apksigner.bat verify --print-certs <apk>
```

A debug-signed APK installs fine, which is exactly what makes this worth checking
before sharing a build.

## Installing on a phone

Over USB, with the phone in developer mode and USB debugging on:

```
adb install -r SMI-APKs/smi-driver-v1.1.0.apk
```

`-r` reinstalls over an existing copy and keeps its data. If it refuses, the
installed app was signed with a different key — uninstall it first, which does
lose its local data.

To share without a cable, send the APK file directly (WhatsApp, Drive, email).
The recipient taps it and allows "install from unknown sources". These are
release builds with the JavaScript bundled in, so they run standalone — no Metro,
no Expo Go, no internet needed to start.

## Troubleshooting

**`TAR_ENTRY_ERROR EPERM` during install** — Windows Defender. Re-run with
`--ignore-scripts`, and make sure you are not inside a sandboxed shell. If
`.name-XXXXXXXX` staging folders or `.DELETE.<hash>` files are left in
`node_modules`, delete `node_modules` and install again; a half-written tree
cannot be repaired file by file.

**Metro cannot resolve a module** — check `apps/<app>/metro.config.js` still
exists. Without it Metro treats the repository root as the project.

**The APK installs but will not update an existing one** — it is debug-signed, or
signed with a different key. Run `apksigner verify --print-certs` and compare
against the keystore above.

**Gradle cannot download its distribution** — download `gradle-9.3.1-bin.zip`
manually and place it in `~/.gradle/wrapper/dists/gradle-9.3.1-bin/<hash>/`,
removing any `.part` or `.lck` files first. The wrapper then unpacks it instead of
fetching.

**`expo prebuild` wants to reach the network** — it is run with `CI=1` and
`EXPO_OFFLINE=1`, which is enough for a normal prebuild. `npm install` still
needs network access.

## iOS

Not built. An iPhone build needs a Mac, or an Apple Developer account at $99/year
for the cloud route. The app code is cross-platform, so `expo prebuild --platform
ios` would generate the Xcode project, but nothing here has been tested for it.
